# 6-29 reinterpret_cast 越界写入（指针类型不匹配造成的安全问题）

## 题目

运行下列的程序，观察执行结果，指出该程序是如何通过指针造成安全性问题的，思考如何避免这个问题的发生。

```cpp
#include <iostream>
using namespace std;
int main(){
    int arr[]={1,2,3};
    double *p=reinterpret_cast<double *>(&arr[0]);
    *p=5;
    cout<<arr[0]<<" "<<arr[1]<<" "<<arr[2]<<endl;
    return 0;
}
```

## 一、运行结果

```text
0 1075052544 3
```

原本是 `1 2 3` 的数组，被改成了 `0 1075052544 3`。

## 二、原因

关键在于两种类型占的字节数不同：`int` 是 4 字节，`double` 是 8 字节。

- `&arr[0]` 是 `int*`，指向数组第一个元素；
- `reinterpret_cast<double*>` 只把「类型标签」换成 `double*`，**地址不变、数据不变**；
- 于是 `*p = 5;` 是往那个地址写入 **8 个字节**的 `double` 值 5.0，
  而 `arr[0]` 和 `arr[1]` 加起来正好 8 个字节，被一并覆盖；`arr[2]` 没被写到。

`5.0` 的 IEEE754 位模式是 `0x4014000000000000`，小端机器上按字节从低到高存放为：

```text
00 00 00 00 00 00 14 40
```

这 8 个字节落在数组上：

| 位置 | 写入的字节 | 当成 int 读出的值 |
| --- | --- | --- |
| `arr[0]` | `00 00 00 00` | 0 |
| `arr[1]` | `00 00 14 40` | `0x40140000` = 1075052544 |
| `arr[2]` | 未被写入 | 3（原值） |

所以输出是 `0 1075052544 3`。那个 1075052544 完全来自浮点数的位模式，被硬当成整数解释了。

## 三、为什么能编译、能运行（安全问题的本质）

1. **编译器管不了**：`reinterpret_cast` 的语义就是「别检查，我知道我在干什么」，语法合法就放行；
2. **属于未定义行为**：拿 `double*` 去写一个 `int` 对象，破坏类型系统；C++ 的严格别名规则
   还允许编译器假设两者不重叠，优化后结果可能更不可预料；
3. **越界写入**：本次数组有 12 字节，写 8 字节还在数组内部，所以"只是"改坏了两个元素。
   如果数组只有 `int arr[]={1};`（4 字节），写 8 字节就会踩到相邻变量、甚至函数返回地址，
   程序可能崩溃，也可能被精心构造的数据劫持控制流 —— 这就是指针造成安全漏洞的典型方式。

## 四、如何避免

1. 指针类型必须与它指向的对象类型一致，不要「贴错标签」再解引用；
2. 数值转换用 `static_cast<double>(x)`（转的是值），不要用 `reinterpret_cast`（转的是地址的解释方式）；
3. 真正需要按字节访问内存时，用 `unsigned char*`（标准明确允许），并且用 `sizeof` 核对边界；
4. 写入前确认目标对象有多少字节，不清楚就不要写。

一句话总结：`reinterpret_cast` 只换类型标签、不换地址，一旦标签和真实对象不匹配，
写入就会越界改坏相邻内存，编译器不会替你把关。
